## 1 Интеграция бэкенда и фронтенда

**Фронтенд** (клиентская часть) — это всё, что видит пользователь на экране и с чем непосредственно взаимодействует в браузере или приложении: кнопки, тексты, картинки, формы ввода и анимации. Код фронтенда выполняется на устройстве пользователя (в браузере), а создается он с помощью таких технологий, как HTML, CSS и TypeScript/JavaScript.

**Бэкенд** (серверная часть) — это скрытая от пользователя «внутренняя кухня» программы или сайта: серверы, базы данных, алгоритмы и бизнес-логика. Он обрабатывает запросы, хранит данные и отвечает за безопасность. Код бэкенда работает на удаленном сервере, а пишут его на таких языках, как C#, PHP, Python, Go, Java.

**Наглядная аналогия (ресторан):**

- **Фронтенд** — это обеденный зал, красивое меню и официант, с которым общается гость.

- **Бэкенд** — это кухня, шеф-повар и продукты в холодильнике, которые гость не видит, но благодаря им появляется еда.

**Почему разделяют бэкенд и фронтенд?**

- **Разделение обязанностей:** Фронтендеры пишут на JS/TS (React, Vue, Angular), бэкендеры — на C#.
- **Кроссплатформенность:** Один Web API обслуживает и Web-сайт, и мобильное приложение (iOS/Android), и десктоп.
- **SPA (Single Page Application):** Браузер один раз скачивает интерфейс, а затем динамически обновляет данные без перезагрузки страниц.

Сейчас наше Web API выполняет роль «чистого» бэкенда. Оно ничего не знает про интерфейс — лишь обрабатывает HTTP-запросы и отдает/принимает данные в формате JSON. Оно написано на языке C# с использованием фреймворка ASP.NET Core.

Во многих промышленных системах фронтенд разрабатывается как отдельное приложение отдельной командой на языке JavaScript или TypeScript с использованием фреймворков React, View или Angular. 

Представим, что у нас есть сторонняя команда, которая разработала фронтенд, и нам нужно подключить к нему наше Web API. Для примера это будет простая статическая HTML-страница со скриптом на JavaScript (`fetch`):

```html
<!-- index.html -->
<!DOCTYPE html>
<html lang="ru">
<head>
    <meta charset="UTF-8">
    <title>Список студентов</title>
</head>
<body>
    <h1>Студенты (Интеграция с Web API)</h1>
    <ul id="students-list"></ul>

    <script>
        // Выносим адрес бэкенда в константу для удобства конфигурации
        const API_BASE_URL = 'http://localhost:5121';

        async function loadStudents() {
            try {
                // Формируем полный путь к эндпоинту контроллера
                const response = await fetch(`${API_BASE_URL}/api/student`);
                
                if (!response.ok) {
                    throw new Error(`Ошибка сервера: ${response.status}`);
                }

                const students = await response.json();
                const list = document.getElementById('students-list');
                
                students.forEach(student => {
                    const li = document.createElement('li');
                    // Внимание: С# свойства Name и Age в JSON превращаются в camelCase (name, age)
                    li.textContent = `${student.name} (Возраст: ${student.age}, Группа: ${student.groupName || 'Нет'})`;
                    list.appendChild(li);
                });
            } catch (error) {
                console.error('Не удалось загрузить данные:', error);
                alert('Произошла ошибка при запросе к бэкенду. Проверьте настройки CORS!');
            }
        }

        // Запуск функции при загрузке страницы
        loadStudents();
    </script>
</body>
</html>
```

### Главный барьер интеграции: Что такое CORS?

Если вы просто запустите этот HTML-файл в браузере (например, через Live Server на порту `5500` или открыв файл напрямую), данные с бэкенда (порт `5121`) **не загрузятся**. В консоли браузера появится красная ошибка.

Это срабатывает **SOP (Same-Origin Policy)** — встроенная система безопасности браузера. Она запрещает скриптам с одного сайта (`localhost:5500`) читать данные с другого сайта (`localhost:5121`), если тот явно не дал на это разрешение. Здесь Origin — адрес, источник, например, адрес Web API или адрес фронтенда. 

Чтобы исправить это, существует технология **CORS (Cross-Origin Resource Sharing)**. Бэкенд должен отправить специальный HTTP-заголовок `Access-Control-Allow-Origin`, сообщающий браузеру: _"Этому сайту я доверяю, ему можно отдать данные"_.

Пример настройки CORS в Web API:
``` csharp
// Файл: Program.cs (в проекте StudentApi)

var builder = WebApplication.CreateBuilder(args);

// 1. РЕГИСТРАЦИЯ ПОЛИТИКИ CORS (Добавляется в секцию сервисов, ДО builder.Build())
builder.Services.AddCors(options =>
{
    options.AddPolicy("AllowLocalFrontend", policy =>
    {
        policy.WithOrigins("http://127.0.0.1:5500", "http://localhost:5500") // URL вашего фронтенда
              .AllowAnyMethod()                                            // Разрешить GET, POST, PUT, DELETE
              .AllowAnyHeader();                                           // Разрешить любые заголовки (Content-Type и т.д.)
    });
});

builder.Services.AddControllers();
// ... другие сервисы (БД, Swagger и т.д.)

var app = builder.Build();

// 2. ВКЛЮЧЕНИЕ CORS В КОНВЕЙЕР (Добавляется строго ПОСЛЕ app.UseRouting(), но ДО app.UseAuthorization() и app.MapControllers())
app.UseRouting();

// Применяем созданную выше политику
app.UseCors("AllowLocalFrontend");

app.UseAuthorization();
app.MapControllers();

app.Run();
```

> [!INFO]
> На этапе разработки, чтобы не мучиться с портами, можно временно использовать метод `.AllowAnyOrigin()` вместо `.WithOrigins(...)`, но на реальном продакшене так делать небезопасно.

## 2 Server-Side Rendering

Клиентская часть не всегда создается как отдельное frontend приложение на JavaScript. В приложениях с простыми интерфейсами мы можем собрать готовый html прямо на сервере в ASP.NET приложении и подставить туда данные с помощью **шаблонизации**.

- **Шаблонизация** — это процесс, когда сервер берет статичный HTML-файл (шаблон) и «вклеивает» в него динамические данные (например, имя студента из базы данных).
- **Razor** — это движок шаблонизации в .NET. Его магия в том, что можно писать обычный C#-код прямо внутри HTML-файла. Достаточно поставить символ `@`, и дальше начинается C#.

При этом код, который подает шаблону данные можно организовать по разному. В ASP.NET Core для этого есть 2 подхода: MVC и Razor Pages. Рассмотрим оба, начнем с MVC.

## 3 Паттерн MVC

**MVC** — это архитектурный паттерн Model-View-Controller.

Приложение разделяется на три основные части:

- Model — данные и бизнес-логика.
- View — HTML-представление.
- Controller — принимает HTTP-запросы, вызывает нужную логику и возвращает результат.

Работа с MVC очень похожа на работу с Web API. **MVC — это практически то же самое Web API, только вместо JSON мы возвращаем View (готовый HTML-шаблон)**:
- В **Web API**: Контроллер берет данные из сервиса -> возвращает `Ok(dto)` (превращается в JSON).
- В **MVC**: Контроллер берет данные из сервиса -> упаковывает в модель страницы -> возвращает `View(model)` (превращается в HTML).

Например, мы хотим сделать страницу со списком студентов и информацией о конкретном студенте.

Структура проекта:

```
StudentMvc/
├── Controllers/
│   └── StudentsController.cs
├── Models/
│   └── StudentViewModel.cs
└── Views/
    └── Students/
        ├── Index.cshtml
        └── Details.cshtml
```

#### Шаг 2. Создаем Модель (ViewModel)

**Где создаем:** Внутри нового проекта `StudentMvc` в существующей папке `Models/`. Создайте файл `StudentListViewModel.cs`.

``` csharp
namespace StudentApi.Mvc.Models;

public class StudentListViewModel
{
    public IEnumerable<StudentItemViewModel> Students { get; set; } = [];
    public string TotalCountMessage => $"Всего студентов в базе: {Students.Count()}";
}

public class StudentItemViewModel
{
    public int Id { get; set; }
    public string DisplayName { get; set; } = string.Empty;
    public string GroupDisplay { get; set; } = string.Empty;
}
```

#### Шаг 3. Создаем Контроллер

**Где создаем:** Внутри нового проекта `StudentMvc` в существующей папке `Controllers/`. Создайте файл `StudentsController.cs`.
Обратите внимание, контроллер в MVC наследуется от `Controller`, а не `ControllerBase` как в Web API.

``` csharp
using Microsoft.AspNetCore.Mvc;  
using StudentApi.Data.Services;  
using StudentMvc.Models.Students;  
  
namespace StudentMvc.Controllers;  
  
// Наследуемся от Controller (для страниц), а не ControllerBase (как в API)  
public class StudentsController : Controller  
{  
    private readonly IStudentService _studentService;  
  
    public StudentsController(IStudentService studentService)  
    {        _studentService = studentService;  
    }  
    // Маршрут по умолчанию: /Student или /Student/Index  
    [HttpGet]  
    public async Task<IActionResult> Index(string? search)  
    {        // 1. Запрашиваем чистые DTO из нашей бизнес-логики  
        var studentsDto = await _studentService.GetAllAsync(search);  
  
        // 2. Превращаем DTO во ViewModel, адаптируя под экран  
        var viewModel = new StudentListViewModel  
        {  
            Students = studentsDto.Select(s => new StudentItemViewModel  
            {  
                Id = s.Id,  
                DisplayName = $"{s.Name} ({s.Age} лет)"            })  
        };  
        // 3. Передаем модель в шаблон. Метод View() автоматически найдет нужный .cshtml файл  
        return View(viewModel);  
    }}
```

#### Шаг 4. Создаем Шаблон (View)

**Где создаем:** В проекте `StudentMvc` зайдите в папку `Views/`. Создайте там новую подпапку с именем контроллера — `Student/`. Внутри неё создайте файл `Index.cshtml`.

_Движок Razor устроен так: для метода `Index` внутри `StudentController` он всегда будет искать файл по строгому пути `Views/Student/Index.cshtml`._

Пишем код разметки с C# элементами:
``` html
@model StudentMvc.Models.Students.StudentListViewModel  
  
@{  
    ViewBag.Title = "Список студентов";  
    Layout = "_Layout";  
}  
  
<h2>@ViewBag.Title</h2>  
<p>@Model.TotalCountMessage</p>  
  
<ul>  
    @foreach (var item in Model.Students)  
    {  
        <li>@item.DisplayName</li>  
    }  
</ul>
```

Теперь, если запустить этот проект и перейти в браузере на `/Student`, сервер выполнит C#-код, подставит данные в таблицу и вернет браузеру чистый, легко читаемый HTML.

Ещё раз обратите внимание на важный момент:
Controller находится в одной папке, View — в другой. Они связаны соглашениями об именовании и маршрутизацией.
Запрос `/students/index` попадёт в `StudentsController`, вызовет метод `Index()`, а тот вернёт представление `Views/Products/Index.cshtml`.

> **Частый вопрос: Почему метод называется Index, а не GetAll?**  
> В Web API мы называем методы по смыслу действий (`GetAll`, `GetById`), потому что маршрут строится вокруг сущностей в URL (`/api/student`).  
> В MVC методы (экшены) привязаны к физическим страницам. Название `Index` — это классический стандарт в веб-разработке (как `index.html`). Оно означает _«главная страница для данного раздела»_. Если пользователь перейдет по адресу `/Student`, сервер по умолчанию вызовет именно метод `Index`. Переименовать в `GetAll` можно, но тогда URL сайта станет `/Student/GetAll`, что менее привычно для пользователя.

## 3 Razor Pages

Мы только что написали список студентов на MVC и заметили одну вещь: чтобы сделать одну простую страницу, нам пришлось создать файлы в совершенно разных частях проекта — в папке `Models`, в папке `Controllers` и в папке `Views`.

Проблемы MVC:

1. **«Размазанный» код:** Внимание постоянно прыгает по структуре проекта. Чтобы поменять логику и внешний вид одной страницы, нужно открыть три папки в разных концах Solution Explorer.
2. **«Толстые» контроллеры:** В одном контроллере со временем скапливаются десятки методов (экшенов) для абсолютно разных страниц, которые никак между собой не связаны, кроме того, что они относятся к одной сущности.

Как Razor Pages решили эту проблему?

**Razor Pages** — это современная надстройка над MVC, ориентированная не на компоненты, а на конкретные веб-страницы. Архитекторы Microsoft подумали: _«Зачем разносить код одной страницы по разным папкам? Давайте объединим View и Controller в одном месте»_.

Каждая страница в Razor Pages состоит из пары тесно связанных файлов, которые лежат в одной папке:

1. `ИмяСтраницы.cshtml` — View (HTML-разметка с элементами Razor).
2. `ИмяСтраницы.cshtml.cs` — PageModel (C#-код, который выполняет роль контроллера конкретно для этой страницы).

При этом под капотом Razor Pages работают на том же самом движке MVC.

Структура:

```
MyApp/
├── Pages/
    ├── Students/
    │   ├── Index.cshtml
    │   ├── Index.cshtml.cs
    │   ├── Details.cshtml
    │   └── Details.cshtml.cs
    └── Index.cshtml
```

Здесь:

- `Index.cshtml` — HTML-разметка.
    
- `Index.cshtml.cs` — C#-логика страницы.

#### Шаг 3. Пишем логику (Код-бехайнд)

**Где открываем:** Файл `Pages/StudentsList.cshtml.cs`.

Вместо методов вроде `Index()` или `GetAll()` в Razor Pages используются обработчики событий, которые начинаются со слова `On` + HTTP-метод. Для загрузки страницы это будет метод **`OnGetAsync`**.

``` csharp
using Microsoft.AspNetCore.Mvc.RazorPages;  
using StudentApi.Data.DTOs.Student;  
using StudentApi.Data.Services;  
  
namespace StudentRazorPages.Pages.Students;  
  
public class Index : PageModel  
{  
    private readonly IStudentService _studentService;  
  
    public Index(IStudentService studentService)  
    {        _studentService = studentService;  
    }  
    // Свойства, в которые мы запишем данные.   
    // Страница .cshtml сможет обратиться к ним напрямую через @Model.Students и @Model.TotalCountMessage  
    public IEnumerable<string> Students { get; set; } = [];  
    public string TotalCountMessage => $"Всего студентов в базе: {Students.Count()}";  
  
    // Обработчик HTTP GET запроса  
    public async Task OnGetAsync(string? search)  
    {        // Напрямую берем данные из сервиса.   
Students = (await _studentService.GetAllAsync(search)).Select(s => $"{s.Name} ({s.Age} лет)");  
    }}
```

#### Шаг 3. Пишем разметку (Шаблон)

**Где открываем:** Файл `Pages/StudentsList.cshtml`.

``` html
@page  
@model StudentRazorPages.Pages.Students.Index  
  
@{  
    ViewBag.Title = "Список студентов";  
    Layout = "_Layout";  
}  
  
<h2>@ViewBag.Title</h2>  
<p>@Model.TotalCountMessage</p>  
  
<ul>  
    @foreach (var item in Model.Students)  
    {  
        <li>@item</li>  
    }  
</ul>
```

Обратите внимание, для написания View используется тот же шаблонизатор Razor, отличие только в директиве `@Page`. Также другая `@model`, она создана автоматически за нас и является частью страницы.
Процесс разработки: мы открываем одну папку, в C#-файле пишем логику получения данных, а в HTML-файле получаем данные через `@Model.` сразу выводим их на экран. Код больше не размазан по всему решению.

## Итог
Сегодня мы разобрали, как бэкенд может взаимодействовать с внешним миром. Мы узнали, что приложение можно разделить на независимый фронтенд и Web API бэкенд, а можно построить в виде монолита на сервере с помощью MVC или более современного подхода Razor Pages.

## Частые ошибки
1. **Путаница с базовыми классами:** При написании Web API контроллеров мы наследуемся от `ControllerBase`. Если вы случайно унаследуетесь от `Controller` (который предназначен для MVC), приложение продолжит работать, но потянет за собой ненужную поддержку View-рендеринга.
2. **Забытый `@model`:** В Razor Pages и MVC-представлениях часто забывают указать директиву `@model` в самом верху `.cshtml` файла, из-за чего C# код внутри разметки не видит переданные сервером данные.

## ❓ Вопросы для самопроверки

# Вопросы для самопроверки — Лекция 7

1. Чем отличаются фронтенд и бэкенд и как они взаимодействуют друг с другом? *(Ответ: Фронтенд — клиентская часть приложения, отвечающая за интерфейс и взаимодействие с пользователем. Бэкенд — серверная часть, отвечающая за бизнес-логику, обработку запросов и работу с данными. Они взаимодействуют через HTTP-запросы и ответы, например с использованием Web API и JSON.)*

2. Что такое MVC и на какие три основных компонента разделяется приложение? *(Ответ: Model — данные и бизнес-логика, View — HTML-представление, Controller — обработка HTTP-запросов и вызов необходимой логики.)*

3. Чем MVC отличается от Web API? *(Ответ: Web API возвращает данные в формате JSON, а MVC возвращает готовое HTML-представление через View(model).)*

4. От какого класса наследуется MVC-контроллер и чем он отличается от ControllerBase? *(Ответ: MVC-контроллер наследуется от Controller, который поддерживает работу с представлениями. ControllerBase используется преимущественно для Web API.)*

5. Что такое ViewModel и зачем она нужна? *(Ответ: ViewModel — модель представления, которая адаптирует данные под конкретный экран и содержит информацию, необходимую для отображения.)*

6. Как MVC связывает контроллер с представлением и где ищет файл View? *(Ответ: По соглашениям об именовании: для StudentsController и метода Index представление ищется в Views/Students/Index.cshtml.)*

7. Что такое Razor Pages и какую основную проблему MVC они решают? *(Ответ: Razor Pages — подход, ориентированный на отдельные страницы. Он объединяет логику и представление страницы в одном месте, избавляя от необходимости искать их в разных папках.)*

8. Из каких двух файлов состоит Razor Page и за что каждый отвечает? *(Ответ: Файл .cshtml содержит HTML-разметку, а .cshtml.cs содержит C#-логику страницы — PageModel.)*

9. Что такое PageModel и от какого класса он наследуется? *(Ответ: PageModel — класс, содержащий логику конкретной Razor Page. Наследуется от Microsoft.AspNetCore.Mvc.RazorPages.PageModel.)*

10. Для чего используются `OnGetAsync`, `@page` и `@model` в Razor Pages? *(Ответ: OnGetAsync обрабатывает GET-запрос и загружает данные; @page обозначает самостоятельную страницу и задает возможность маршрутизации; @model указывает класс PageModel, связанный с представлением.)*

11. В чем основные различия MVC и Razor Pages? *(Ответ: MVC организует приложение вокруг Model, View и Controller, размещенных в разных папках. Razor Pages организует приложение вокруг отдельных страниц, объединяя представление и его логику в паре файлов .cshtml и .cshtml.cs.)*
