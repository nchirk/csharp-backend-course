# Лекция 5. EF Core — связь 1:N, миграции и конфигурация моделей

Цель занятия: научиться применять миграции, освоить расширенную конфигурацию моделей через Fluent API и изучить принципы построения связей между сущностями в EF Core.

## 1. Обновление базы при изменении кода, миграции

На прошлом занятии мы:
* описали базу данных через *Code First* (класс `AppDbContext` = БД `students.db`, класс `Student` = Таблица `Student`)
* сгенерировали базу данных с помощью `db.Database.EnsureCreated();`

`EnsureCreated()` создает базу данных однократно. Он не может добавить в существующую базу данных новые таблицы и колонки. Для обновления БД используется механизм **миграций**.

### Механизм миграций

При изменении классов-сущностей кодовая база и реальная БД рассинхронизируются. Для обновления структуры используются миграции.

* При вызове команды `Add-Migration` EF Core сравнивает текущий снимок модели с кодом и генерирует C#-класс с методами `Up()` (применение изменений) и `Down()` (откат изменений).
* В самой базе данных EF Core создает техническую таблицу `__EFMigrationsHistory`. В ней хранятся два столбца: `MigrationId` (название файла миграции с временной меткой) и `ProductVersion`. При запуске Update-Database (в графическом интерфейсе или консоли) EF Core проверяет эту таблицу и выполняет только те миграции, которых там ещё нет.

### Реализация на практике

#### Подготовка к использованию миграций
В существующей БД `students.db` нет `__EFMigrationsHistory`, нужно воссоздать её и начальную миграцию вручную либо просто удалить БД. Для простоты удалим.

1. Откройте проводник вашего проекта и **вручную удалите файл `students.db`** (а также файлы `students.db-shm` и `students.db-wal`, если они создались рядом).
2. Уберите из конструктора `StudentsController` метод `db.Database.EnsureCreated()` — он нам больше не понадобится.

```csharp
public class StudentController : ControllerBase
{
    private readonly AppDbContext db;
    
    public StudentController(AppDbContext db)
    {
        this.db = db;
        //здесь был вызов db.Database.EnsureCreated()
    }

    // методы контроллера...
}
```
3. Установите в проект пакет для работы с миграциями: нажмите вкладку NuGet внизу экрана, введите в поиск `Microsoft.EntityFrameworkCore.Design`, выберите проект и нажмите [+] (Install).
4. Убедитесь, что проект успешно компилируется и в нем настроена строка подключения к базе данных.

#### Добавление начальной миграции

В JetBrains Rider управление миграциями осуществляется через графический инструмент **Entity Framework Core tools**.

1. **Открытие инструмента EF Core:**
   * В верхнем меню выберите: **Tools** -> **Entity Framework Core**.
   * *Альтернатива:* щелкните правой кнопкой мышки по проекту и выберите пункт **Entity Framework Core**.
   * *Альтернатива:* Нажмите **Ctrl + Shift + A** (Find Action), введите `EF Core` и выберите пункт **Entity Framework Core**.

2. **Настройка базовых параметров в окне:**
   * **Migrations project:** Укажите проект, в котором находится ваш класс контекста данных (`DbContext`). Именно сюда сохранится папка с файлами миграций. *Пока у нас только один проект, везде указываем его.*
   * **Startup project:** Выберите ваш главный исполняемый проект (тот, куда был установлен пакет `.Design`). *Пока у нас только один проект, везде указываем его.*
   * **DbContext class:** Выберите из выпадающего списка нужный контекст (если их несколько). *AppDbContext*

3. **Добавление миграции:**
   * В этом же окне перейдите на вкладку **Migrations**.
   * В текстовом поле **Name** задайте осмысленное имя для первой миграции (по стандарту: `Initial` или `InitialCreate`).
   * Нажмите кнопку **Add** (или зеленую стрелку). Rider соберет проект и сгенерирует файлы миграции в коде.

#### Обновление базы данных (применение миграции)

После создания файлов кода миграции их необходимо физически применить к серверу базы данных, чтобы создать таблицы.

1. В графическом окне **Entity Framework Core** переключитесь на вкладку **Database**.
2. Проверьте, что параметры проектов (*Migrations*, *Startup* и *DbContext*) выставлены верно.
3. Нажмите кнопку **Update**.
4. В нижней панели Rider откроется лог выполнения. При успешном завершении в вашей СУБД появится готовая база данных, таблицы сущностей и служебная таблица `__EFMigrationsHistory`.

Посмотрите, как изменилось содержимое проекта и что создалось в базе данных.


#### Применение дальнейших изменений

Чтобы изменить базу:
1. Отредактируйте классы моделей (у нас `Student`) или добавьте новый DbSet в DbContext (у нас `AppDbContext`)
2. Создайте новую миграцию. Название — в **PascalCase**
3. Обновите базу. Изменения появятся в базе.

> [!CAUTION]
> **ВАЖНОЕ ПРЕДОСТЕРЕЖЕНИЕ:**
> * **Создание миграции НЕ обновляет базу автоматически!** Команда добавления миграции только генерирует файлы C#-кода с инструкциями. Чтобы физически изменить таблицы на сервере, необходимо отдельно запустить процесс обновления базы данных (`Update`).
> * **Забудьте про ручное изменение таблиц!** Теперь вы работаете по подходу *Code-First*. Любые изменения в структуру базы данных вносятся исключительно через редактирование классов моделей и создание новых миграций. Прямое редактирование таблиц в СУБД гарантированно сломает дальнейшую работу проекта.

Проверим, как работает механизм изменения структуры данных (подход *Code-First*). Добавим в таблицу Student колонку Age.


1. **Модификация кода:**
   * Откройте файл класса `Student.cs`.
   * Добавьте новое свойство для хранения возраста:
     ```csharp
     public int Age { get; set; }
     ```

2. **Создание новой миграции:**
   * Откройте инструмент **Entity Framework Core** (или консоль).
   * Создайте новую миграцию. Дайте ей понятное имя, отражающее суть изменений, например: `AddStudentAge`.
   * Убедитесь, что в папке `Migrations` появился новый файл, внутри которого в методе `Up` прописана команда `AddColumn`.

3. **Обновление базы данных:**
   * Запустите команду **Update** (или `database update` в CLI).
   * Откройте вашу СУБД (через вкладку *Database* в Rider или внешний клиент) и убедитесь, что в таблице `Students` появилась новая колонка `Age`.

## 2. Настройка связей

В реальных базах данных таблицы редко существуют изолированно. EF Core позволяет проецировать объектные связи (ссылки и коллекции объектов в C#) в реляционные связи (внешние ключи Foreign Keys в SQL).

Различают три основных типа связей:

* **Один ко многим (1:N)**: Самый частый случай. У одной группы (`Group`) много студентов (`Student`), но студент принадлежит только к одной группе.

* **Один к одному (1:1)**: У одного студента есть одна зачетная книжка (`StudentCard`).

* **Многие ко многим (N:M)**: Один студент может выполнять много лабораторных работ (`LabRequirement`), и одну лабораторную работу могут выполнять много студентов. В EF Core 5+ промежуточная таблица генерируется автоматически, если сущности содержат коллекции друг друга.

Добавим таблицу Group со связью 1:N. Связи N:M и 1:1 рассмотрим на следующей лекции.

### Реализация на практике

Новый класс `Models/Group.cs`

```csharp

namespace StudentApiWithDB.Models;

public class Group

{

    public int Id { get; set; }

    public string Name { get; set; } = string.Empty;


    // Навигационное свойство: у одной группы много студентов

    public ICollection<Student> Students { get; set; } = new List<Student>();

}

```
 
Модифицируем существующий класс `Student.cs`:

```csharp

namespace StudentApiWithDB.Models;

public class Student

{

    public int Id { get; set; }

    public string FirstName { get; set; } = string.Empty;

    public string LastName { get; set; } = string.Empty;

    public int Age { get; set; }


    // Связь 1:N (Студент принадлежит группе)

    public int? GroupId { get; set; }

    // Навигационное свойство

    public Group? Group { get; set; } 

}

```

Регистрируем новую таблицу в контексте данных:

`Data/AppDbContext.cs`

```csharp

using Microsoft.EntityFrameworkCore;
using StudentApiWithDB.Models;

namespace StudentApiWithDB.Data;

public class AppDbContext : DbContext
{
    public AppDbContext(DbContextOptions<AppDbContext> options) : base(options) { }

    public DbSet<Student> Students => Set<Student>();

    public DbSet<Group> Groups => Set<Group>();

}
```

Редактируем `StudentController` (теперь там не обязательный `GroupName`, а опциональный `GroupId`), добавляем `GroupController`. Вместо одного большого файла `StudentApiWithDB.http` делаем два отдельных `student.http` и `group.http` для тестирования методов API в контроллерах.

*При запросе группы в `group.http` список студентов будет пустым — это нормально (ленивая загрузка данных), разберем на следующей лекции.*

После добавления таблицы и связи обязательно зафиксируйте изменения в базе данных. Для этого в графическом интерфейсе Rider (вкладки **Migrations** и **Database**) или через консоль последовательно выполните две команды:

1. **Создание миграции** (генерирует код создания таблицы):
   ```bash
   dotnet ef migrations add AddGroup
   ```
2. **Обновление базы данных** (применяет ограничения в СУБД):
   ```bash
   dotnet ef database update

## 3. Настройка ограничений через Fluent API

По умолчанию **EF Core** настраивает базу данных по **конвенциям (соглашениям)**: например, свойство с именем `Id` автоматически становится первичным ключом, а тип `string` превращается в тип `TEXT` без ограничения длины (в SQLite) или в `nvarchar(max)` (в MS SQL Server).

Для кастомизации ограничений (установка обязательных полей, ограничение длины, уникальность, индексы) используются два подхода:
1. **Data Annotations (Атрибуты):** Размечаются прямо над свойствами в сущностях (например, `[Required]`, `[MaxLength(50)]`). *Минус:* засоряет бизнес-модели инфраструктурным кодом БД.
2. **Fluent API:** Настройка внутри метода `OnModelCreating` контекста. Позволяет полностью отделить конфигурацию базы данных от бизнес-логики.

Реализовать Fluent API можно двумя способами:
* **Прямо в OnModelCreating:** Писать весь код конфигурации кучей внутри контекста. Подходит только для маленьких проектов.
* **Через IEntityTypeConfiguration<T> (Рекомендуемый):** Вынести конфигурацию каждой сущности в отдельный выделенный класс. Это делает проект чистым, масштабируемым и легко читаемым.

### Реализация на практике

Создадим папку `Data/Configurations` и добавим туда отдельные классы конфигурации для сущностей `Student` и `Group`.

#### Конфигурация для сущности Student
Создаем файл `Data/Configurations/StudentConfiguration.cs`:

```csharp
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Metadata.Builders;
using StudentApiWithDB.Models;

namespace StudentApiWithDB.Data.Configurations;

public class StudentConfiguration : IEntityTypeConfiguration<Student>
{
    public void Configure(EntityTypeBuilder<Student> builder)
    {
        // Установка первичного ключа (необязательно, если имя Id, но полезно для явности)
        builder.HasKey(s => s.Id);

        // Установка обязательных полей и ограничений длины строки
        builder.Property(s => s.FirstName)
            .IsRequired()
            .HasMaxLength(50);

        builder.Property(s => s.LastName)
            .IsRequired()
            .HasMaxLength(60);

        // Явное указание связи один-ко-многим (хотя EF Core понимает её и по конвенциям)
        builder.HasOne(s => s.Group)
            .WithMany(g => g.Students)
            .HasForeignKey(s => s.GroupId)
            .OnDelete(DeleteBehavior.SetNull); // При удалении группы студенты остаются, но их GroupId зануляется
    }
}
```

#### Конфигурация для сущности Group
Создаем файл `Data/Configurations/GroupConfiguration.cs`. Здесь мы зададим **ограничение по длине** для имени группы и сделаем это имя **уникальным** с помощью индекса.

```csharp
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Metadata.Builders;
using StudentApiWithDB.Models;

namespace StudentApiWithDB.Data.Configurations;

public class GroupConfiguration : IEntityTypeConfiguration<Group>
{
    public void Configure(EntityTypeBuilder<Group> builder)
    {
        // Установка первичного ключа
        builder.HasKey(g => g.Id);

        // Имя группы обязательно для заполнения и не должно превышать 20 символов
        builder.Property(g => g.Name)
            .IsRequired()
            .HasMaxLength(20);

        // Создание уникального индекса: в базе данных не может быть двух групп с одинаковым именем
        builder.HasIndex(g => g.Name)
            .IsUnique();
    }
}
```

#### Регистрация конфигураций в DbContext

Чтобы EF Core увидел наши новые классы конфигурации, их необходимо подключить в контексте базы данных. Вместо того чтобы регистрировать каждый класс вручную, мы используем метод автоматического сканирования сборки.

Файл `Data/AppDbContext.cs`:

```csharp
using Microsoft.EntityFrameworkCore;

namespace StudentApiWithDB.Data;

public class AppDbContext : DbContext
{
    // Здесь находятся ваши DbSet<Student> и DbSet<Group>...

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        base.OnModelCreating(modelBuilder);

        // Автоматически находит и применяет ВСЕ конфигурации (наследники IEntityTypeConfiguration), 
        // которые находятся в текущей сборке проекта.
        modelBuilder.ApplyConfigurationsFromAssembly(typeof(AppDbContext).Assembly);
    }
}
```

После настройки ограничений во **Fluent API** обязательно зафиксируйте изменения в базе данных. Для этого в графическом интерфейсе Rider (вкладки **Migrations** и **Database**) или через консоль последовательно выполните две команды:

1. **Создание миграции** (генерирует код ограничений):
   ```bash
   dotnet ef migrations add ConfigureStudentAndGroup
   ```
2. **Обновление базы данных** (применяет ограничения в СУБД):
   ```bash
   dotnet ef database update
   ```

⚠️ **Предупреждение:** Если в базе данных уже есть группы с одинаковыми именами, шаг обновления **вызовет ошибку**. СУБД откажется создавать уникальный индекс, пока дубликаты не будут удалены вручную.

## ❓ Вопросы для самопроверки
1. Какое главное ограничение у метода EnsureCreated()? *(Ответ: Создает БД однократно и не умеет добавлять новые таблицы или колонки в существующую базу)*
2. Зачем нужна техническая таблица __EFMigrationsHistory? *(Ответ: Хранит список уже примененных миграций, чтобы EF Core не запускал их повторно)*
3. Применяется ли миграция в БД автоматически сразу после команды Add-Migration? *(Ответ: Нет, команда лишь генерирует C#-код; для изменения таблиц в СУБД нужно отдельно запустить Update-Database)*
4. Какие три основных типа связей между таблицами поддерживает EF Core? *(Ответ: Один ко многим 1:N, один к одному 1:1 и многие ко многим N:M)*
5. Как в коде C# связать сущности Student и Group отношением 1:N? *(Ответ: Добавить коллекцию ICollection<Student> в класс Group, а в класс Student — ссылку Group и внешний ключ GroupId)*
6. Как зарегистрировать новую модель в контексте AppDbContext? *(Ответ: Добавить в класс контекста свойство типа DbSet<ИмяМодели>)*
7. В чем главное преимущество Fluent API перед Data Annotations (атрибутами)? *(Ответ: Полностью отделяет конфигурацию базы данных от бизнес-логики, оставляя классы моделей чистыми)*
8. Какой интерфейс используется для вынесения конфигурации сущности в отдельный класс? *(Ответ: IEntityTypeConfiguration<T> с методом Configure)*
9. Как автоматически подключить все конфигурации из проекта в OnModelCreating? *(Ответ: Вызвать метод modelBuilder.ApplyConfigurationsFromAssembly(typeof(AppDbContext).Assembly))*
